2026 ABC 프로젝트 멘토링 15기 프로젝트가 시작됐다.
첫날에는 팀이 DDBM Canvas로 프로젝트의 방향을 정리했고, 나는 **RAG 구현**을 맡았다.
이 글에서는 캔버스 내용을 정리하고, 그중 내가 맡은 RAG와 맞닿는 부분을 따로 뽑아 본다.

## 프로젝트 한눈에 보기

주제는 **LLM 기반 지능형 업무 지원 서비스 연구 개발**이다.

사내 블로그에 흩어진 운영 매뉴얼과 장애 대응 기록을 검색 가능한 지식베이스로 구축한다.
직원이 업무 상황을 입력하면 LLM이 관련 문서를 찾아 점검 항목을 안내하고,
직원이 입력한 점검 결과로 팀 공유용 보고 초안을 작성한다.

| 구분 | 내용 |
| --- | --- |
| 주요 사용자 | 담당자 부재 시 업무를 대신 처리하는 직원, 운영 절차에 익숙하지 않은 신규 팀원 |
| 핵심 기능 | 사내 문서 검색, 출처가 붙은 대응 체크리스트 생성, 점검 결과를 반영한 보고 초안 작성 |
| 초기 시연 | GitLab 배포 작업이 대기 상태일 때 Runner 상태와 작업 태그를 확인하고 진행 상황을 보고하는 과정 |

서비스의 흐름은 다음과 같다.

1. 직원이 업무 상황을 입력한다.
2. 상황에 맞는 사내 문서 구간을 검색한다.
3. 검색된 구간을 근거로 출처가 붙은 점검 체크리스트를 제시한다.
4. 직원이 항목별 점검 결과를 입력한다.
5. 확인된 사실과 추가 확인이 필요한 사항을 구분해 보고 초안을 작성한다.

## 왜 만드는가

### 미션

담당자가 자리를 비우거나 신규 인력이 투입되어도 팀원이 필요한 업무 지식을 찾아 대응을 이어갈 수 있게 한다.
구성원이 기록한 해결 경험을 다음 담당자도 활용할 수 있는 조직의 자산으로 축적한다.

- **업무 연속성**: 담당자에게 바로 물어보기 어려운 상황에서도 기존 운영 절차와 유사 사례를 확인할 수 있도록 지원한다.
- **인수인계 지원**: 신규 담당자가 확인 순서, 판단 근거, 보고에 포함할 내용을 한곳에서 파악할 수 있도록 지원한다.
- **업무 지식 재사용**: 블로그에 쌓인 해결 과정과 운영 노하우를 유사 상황에서 다시 활용한다.

### 가치제안

직원이 업무 상황을 입력하면 어디부터 확인할지, 그 근거는 무엇인지, 팀에 어떤 내용으로 공유할지를 한 화면에서 확인할 수 있다.

- **상황별 점검 안내**: GitLab 배포 작업이 대기 상태라면 Runner 상태와 작업 태그 등 관련 문서에서 확인할 항목을 찾아 순서대로 제시한다.
- **근거 열람**: 점검 항목마다 출처를 표시해 직원이 운영 절차와 유사 사례의 원문을 바로 확인한다.
- **보고 초안 작성**: 직원이 입력한 결과를 바탕으로 확인된 사실과 추가 확인이 필요한 사항을 구분해 팀 공유용 초안을 생성한다.

### 혜택

| 대상 | 기대 효과 |
| --- | --- |
| 직원 | 익숙하지 않은 업무에서도 확인 순서와 근거를 파악하고, 보고 초안 작성에 드는 시간을 절감한다. |
| 운영팀 | 필수 점검 항목과 보고 형식을 공유해 인수인계 과정의 정보 누락과 보고 편차를 줄인다. |
| 조직 | 기존 문서의 활용도를 높이고, 근거를 찾기 어려웠던 질문을 바탕으로 매뉴얼 보완 대상을 파악한다. |

## 무엇을, 누구와 만드는가

### 핵심 활동

사내 문서를 업무 상황에 맞게 검색할 수 있도록 정리하고, 검색 결과가 점검과 보고로 이어지는 기능을 개발한다.

- **문서 수집·정리**: 블로그 글과 매뉴얼을 등록하고 업무 유형, 수정일, 출처, 열람 권한을 기록한다.
- **검색·초안 생성**: 상황에 맞는 문서 구간으로 체크리스트를 만들고, 직원이 입력한 점검 결과를 보고 양식에 반영한다.
- **효과 검증**: 직접 문서를 검색하는 방식과 비교해 보고 초안 작성 시간, 필수 점검 항목 누락 수, 안내와 원문 근거의 일치 여부를 측정한다.

### 핵심 이네이블러

문서 등록과 권한 관리, 검색증강생성(RAG), 보고 양식을 연결해 직원이 검색 결과를 실제 업무에 활용할 수 있게 한다.

- **문서 관리 기능**: 문서 등록 시 업무 유형, 수정일, 출처, 열람 권한을 함께 저장하고 변경된 내용을 검색에 반영한다.
- **검색증강생성(RAG)**: 키워드와 문장 의미를 활용해 관련 문서 구간을 찾고, 해당 구간을 근거로 점검 항목을 생성한다.
- **점검·보고 화면**: 직원이 항목별 점검 결과를 입력하고, 정해진 양식으로 작성된 보고 초안을 검토·수정한다.

### 핵심 데이터

| 종류 | 내용 |
| --- | --- |
| 업무 문서 | 사내 블로그 글, 운영 매뉴얼, 배포 절차, 장애 대응 기록, 자주 묻는 질문, 상황 보고 양식 |
| 문서 관리 정보 | 제목, 업무 유형, 작성 부서, 최종 수정일, 원문 링크, 열람 권한 |
| 업무·평가 데이터 | 직원이 입력한 상황과 점검 결과, 시나리오별 기준 문서, 필수 점검 항목, 보고 초안 작성 시간 |
| 초기 시연 자료 | 내부 식별 정보를 제거한 문서 또는 GitLab 배포 지연 시나리오에 맞춰 작성한 샘플 문서 |

### 핵심 파트너

문서를 관리하는 담당자와 실제 업무를 수행하는 직원이 함께 자료 범위와 검증 기준을 정한다.

- **IT 운영팀·문서 작성자**: 업무 매뉴얼과 대표 사례를 제공하고, 생성된 점검 항목이 실제 운영 절차에 맞는지 검토한다.
- **블로그 관리자·정보보안 담당자**: 연동할 문서 범위, 사용자별 열람 권한, 민감정보 처리 기준을 협의한다.
- **시범 사용 부서**: 기존 방식과 플랫폼으로 같은 상황을 처리하고, 사용 중 막히는 지점과 보고 초안 수정 사항을 공유한다.

## 무엇이 어려운가

### 핵심 장벽

사내 문서의 품질과 최신성이 일정하지 않고, 서비스 연동 과정에서 원문의 열람 권한을 검색과 응답에도 반영해야 한다.

- **문서 품질 편차**: 오래된 글과 최신 매뉴얼이 함께 남아 있거나 부서별 용어가 달라 필요한 절차를 찾기 어렵다.
- **시스템 연동과 권한 관리**: 블로그마다 문서를 가져오는 방식이 다르고, 사용자별 열람 범위를 검색 결과에도 적용해야 한다.
- **현업 검증 부담**: 절차가 바뀔 때 기준 문서를 갱신하고 생성된 점검 항목을 검토할 담당자가 필요하다.

### 부정적 영향과 대응

부정확한 안내가 장애 대응을 지연시키거나, 권한 밖의 내부 정보가 답변에 포함될 수 있다.
그래서 생성된 안내와 보고 초안을 직원이 확인할 수 있도록 근거와 점검 상태를 함께 표시한다.

| 위험 | 대응 |
| --- | --- |
| 잘못된 조치 | 문서 수정일과 출처를 표시하고, 근거가 부족한 항목은 '추가 확인 필요'로 표시한다. |
| 내부 정보 노출 | 검색 단계에서 사용자 열람 권한을 적용하고, 등록 문서에서 비밀번호와 인증 토큰 등 민감정보를 제거한다. |
| 추정의 사실화 | 보고 초안에서 직원이 직접 확인한 사실과 시스템이 제안한 점검 항목을 구분하고, 검토 후 공유한다. |

## 비용과 수익

### 비용

초기에는 문서 정리와 기능 개발에 인력이 필요하며, 운영 단계에서는 모델 사용량과 문서 갱신에 따라 비용이 발생한다.

- **초기 개발비**: 문서 수집·정제, 검색과 보고 초안 생성 기능 개발, 화면 설계, 시나리오 검증에 인력 비용이 든다.
- **운영비**: LLM 호출, 문서 임베딩, 검색용 데이터베이스와 서버 운영, 변경 문서 갱신 및 품질 검토에 비용이 든다.
- **기업별 도입비**: 기존 블로그와 사내 인증 연동, 부서별 권한 설정, 기업별 보고 양식 적용에 비용이 든다.

### 수익

기업·팀 단위 구독을 기본 수익 모델로 설정한다.
기존 시스템 연동 범위와 고객사의 설치 방식에 따라 초기 구축 및 운영 지원 비용을 책정한다.

- **정기 구독료**: 이용 인원과 월간 사용량에 따라 문서 검색, 체크리스트 생성, 보고 초안 작성 기능을 제공한다.
- **초기 구축비**: 블로그 연동, 기존 문서 이관, 부서별 권한 설정, 기업별 보고 양식 적용에 대해 한 번 청구한다.
- **구축·유지보수 계약**: 사내 인프라에 설치해야 하는 기업을 대상으로 설치, 업데이트, 운영 지원을 제공한다.

## 내가 맡은 부분: RAG 구현

캔버스에서 RAG와 직접 맞닿는 요구사항을 뽑아 보면 다음과 같다.

| 단계 | 캔버스에서 요구하는 것 |
| --- | --- |
| 문서 등록 | 업무 유형, 수정일, 출처, 열람 권한을 문서와 함께 저장하고, 변경된 내용을 검색에 반영한다. |
| 민감정보 처리 | 등록 문서에서 비밀번호와 인증 토큰 등 민감정보를 제거한다. |
| 검색 | 키워드와 문장 의미를 함께 활용해 상황에 맞는 문서 구간을 찾는다. |
| 권한 적용 | 사용자별 열람 권한을 검색 단계에서 적용해 권한 밖 문서가 답변에 섞이지 않게 한다. |
| 생성 | 검색된 구간을 근거로 점검 항목을 만들고, 항목마다 출처와 문서 수정일을 표시한다. |
| 근거 부족 처리 | 근거가 부족한 항목은 '추가 확인 필요'로 표시한다. |
| 평가 | 안내와 원문 근거의 일치 여부, 필수 점검 항목 누락 수, 보고 초안 작성 시간을 측정한다. |

정리하면 이 프로젝트의 RAG는 답을 그럴듯하게 만드는 것보다 **근거를 확인할 수 있게 만드는 것**이 핵심이다.
직원이 점검 항목의 원문을 바로 열어 볼 수 있어야 하고, 오래된 절차나 권한 밖의 정보가 답변에 들어가면 안 된다.

### 앞으로 정해야 할 것

첫날이라 아직 정해진 것보다 정해야 할 것이 많다. RAG 구현을 시작하기 전에 답해야 할 질문을 적어 둔다.

- 문서를 어떤 단위로 나눠야 점검 항목의 근거로 쓰기 좋은가
- 키워드 검색과 의미 검색을 어떻게 결합할 것인가
- 열람 권한과 수정일 같은 문서 관리 정보를 검색에 어떻게 반영할 것인가
- 근거가 부족하다는 것을 무엇을 기준으로 판단할 것인가
- GitLab 배포 지연 시나리오의 기준 문서와 필수 점검 항목을 어떻게 준비할 것인가

다음 글에서는 이 질문들에 대한 답을 하나씩 정리해 보겠다.
